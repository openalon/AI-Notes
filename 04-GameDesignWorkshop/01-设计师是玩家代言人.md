# 第 1 章：设计师是玩家代言人

## 一句话

**设计师的主业不是控制游戏怎么运转，而是先写下玩家该感到什么，再反复试玩，直到系统真的能把那种感觉交出来。** 图形、剧情、新功能都可能把你从玩家身边拖走。

## 核心概念

### Advocate for the player

开篇就把角色定死：设计师 envision 玩的时候会发生什么——目标、规则、程序、戏剧前提——然后对交付时的 **gameplay** 负责。美术总监管画面，制作人管预算，技术总监管引擎。你管的是：交出去的时候，人还想继续玩。

Fullerton 的警告很具体：做着做着你会爱上自己加的特效和设定，客观性会掉。这时和「未来那个新玩家」的视角已经错开了。补救不是再自我感觉一次，而是把 **playtesters** 拉进来：看他们盯哪、卡在哪、什么时候无聊，把他们说的每一句记下来。他们是你钻回游戏内部的向导。

她用办派对作比：你只能把食物、酒、灯光、音乐摆好，门打开以后发生什么才是体验。游戏是单向传播的反面——你搭的是潜能，不是成品独白。

### 为什么不能把试玩拖到太晚

常见借口：档期紧、功能还不够、找人贵、那是大厂市场部的事。她的反驳是：离婚式地离开反馈，通常更费时间、钱和心气。因为你不是在写一部自己能控每一帧的电影。

Exercise 1.1 要求先观察自己玩，再观察别人玩同一款，对照两份笔记。这不是暖场，是后面整本书的感官训练。

### Playcentric = 体验目标当试金石

迭代的定义很朴素：设计、测试、评估，一遍遍改玩法或功能，直到玩家体验满足你事先写下的标准。流程是：

1. 设定 player experience goals
2. 构思一个想法或系统
3. 做成原型（物理、数字，甚至分镜 / animatic）
4. 拿给潜在玩家试或看
5. **用体验目标评估结果**（不是用「我们做完了没」）
6. 排序问题，改原型
7. 再测，再对照目标
8. 重复，直到试玩结果符合体验目标

生产开始之后再改软件设计会越来越贵。所以她建议：**没有想清楚体验目标和核心机制，不要开工。**

### 从 Ideation 到制作的七步

书把循环展开成可执行的阶段（五版已经把第一步叫 Ideation，和第 6 章改名对齐）：

| 步 | 做什么 | 停手条件 |
|---|---|---|
| 1 Ideation | 定体验目标；想概念；收成 top 3；一页 concept / 3–6 页 treatment；拿文字概念去测 | 有人能从纸上感到你要的体验 |
| 2 Physical prototype | 纸笔或手工材料做成能玩的 | 纸面玩法已经符合体验目标，再写 gameplay treatment |
| 3 Presentation（可选） | 用草稿图 + treatment 要资源或对齐团队 | 没拿到钱就改概念；此时还没砸美术和程序 |
| 4 Software prototype | 廉价临时图，多个数字原型各打一块 | 数字玩法符合目标，再规划完整功能和关卡 |
| 5 Design documentation | 原型里学到的写成团队用得上的目标清单 | 文档是协作工具，会随制作长；可以是 wiki / 一页纸 / macro，不是开天之作 |
| 6 Production | 按目标 sprint；每轮仍对照体验目标 | 大问题应已在原型期死掉，这里只剩越来越小的改 |
| 7 Post / QA | 抛光 | 仍是同一套循环，不是另一套哲学 |

### Zimmerman：迭代是研究，不是返工

Eric Zimmerman 的侧栏把方法说成：原型 → 测 → 分析 → 精炼，循环。**和进行中的系统互动，才是设计过程本身。** 玩家体验无法完全预判，所以决定必须基于「这个原型被玩起来怎样」。

他拿 SiSSYFiGHT 2000 当案例：先写下 play values（面向非玩家、低技术门槛、好学但深、天生社交、贴合 Word.com 的聪明反讽），再头脑风暴，才长出「操场上小女孩的社交冲突」。对照的是零售游戏里那种「先写穷尽一切的 design document」——最终游戏几乎从不长成那份文档。

## 关键洞察

- **控制欲是业余标志。** 专业是把零件摆好，让体验在玩家进来以后展开。
- **体验目标不是愿望清单，是验收标准。** 没有它，试玩意见无法排序，迭代会变成「谁嗓门大改谁的」。
- **纸面原型不是寒酸，是故意把成本留在可逆区间。** 数字原型用临时图，也是同一纪律。
- **文档后置。** 先玩起来，再把学到的写成团队能改的协作物。大静态文档是假确定性。
- 章末「Designers You Should Know」把 Miyamoto、Garriott、Dona Bailey、Gerald Lawson、Carol Shaw、Danielle Bunten Berry 放在一起：提醒你玩法史比引擎史长，而且从来不是单一人口的行业。

## 个人思考

和 [[00-序言]] 里「模型是不稳部件，harness 负责收拾」是同构：这里不稳的是设计师的自我感觉。Playtest loop 就是游戏设计的 query loop——上一轮留下的问题必须能进入下一轮，而且对照的是目标，不是进度条。

练习 1.1 值得真做一次，不要跳。下一章用 Go Fish 和 Quake 证明：表面上毫无关系的两款游戏，共享同一套结构零件。
