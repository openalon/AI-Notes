# 第 3 章：工具调用

<summary>出处</summary>
<p>来源：<a href="https://github.com/anthropics/claude-cookbooks/tree/main/tool_use">tool_use/</a> · 状态：已读</p>

## 一句话

**工具把模型从「会说」变成「能做」；真正的约束是 schema、choice、谁在调用、结果进不进上下文。** 计算器是教具，PTC 和 tool search 才是规模问题。

## 核心概念

### 最小工具：模型不算，工具算

`tool_use/calculator_tool.ipynb` 是入门环：定义 schema → 模型发 `tool_use` → 你执行 → `tool_result` 回去。评测是演示用的。真正要带走的是：**算术、IO、副作用都不该发生在 token 里。**

### `tool_choice` 是控制面，不是开关

`tool_use/tool_choice.ipynb`：`auto`（模型决定）、`tool`（强制某一工具）、`any`（必须用工具但不能指定哪把）。强制抽取走 `tool`；开放对话走 `auto`；「这轮必须动手」走 `any`。和 Book 1 [[04-工具权限与中断]] 同构：权限不在散文里，在这一轮允许什么。

### 并行、Pydantic、客户端完整环

- `parallel_tools.ipynb`：一次多工具降延迟。3.7 一代曾用 `batch_tool` 绕过限制；现在看官方并行语义，不要把 workaround 当永恒 API。
- `tool_use_with_pydantic.ipynb`：schema 从类型来。工具的输入输出都应该能被校验，散文描述只是给人看的。
- `customer_service_agent.ipynb` / `threat_intel_enrichment_agent.ipynb`：完整客户端环——多源工具、结构化报告、循环直到停。威胁情报那份强调：报告形状第 1 章就该钉死，工具只负责填。
- `vision_with_tools.ipynb`：看图和动手叠在一起。图是输入模态，工具是行动权；不要把「能看见」当成「能改」。

### PTC：让代码调工具，不让每一跳都过模型

`programmatic_tool_calling_ptc.ipynb` 用模拟费用 API：`get_team_members` → 每人上百条带元数据的 `get_expenses` → 超标再查 `get_custom_budget`。传统 tool use 把全部行项目灌进上下文，再串行 round-trip。

PTC：模型在 **code execution** 里写代码调工具；大结果在沙箱里 grep / 聚合，只有摘要回模型。要点：

- 工具要加 `allowed_callers`；默认只许模型直接调。
- 可同时 `["direct", "code_execution_20250825"]`。
- 只对 **安全、可重复执行** 的工具开放 programmatic。
- `caller` 字段区分 direct / code；**只有 direct 的结果会被模型看见**。
- 走 beta：`advanced-tool-use-2025-11-20`，有状态工作流要带 `container_id`。

示例里 PTC 的 API 调用次数可能更多（代码写得更结构化、步骤拆开），省的是 **token 和延迟**，不是请求数。第 10 章 agentic search 复现把 PTC 当成深搜的第一杠杆：50+ 次 fetch 若每页都进对话，窗口会先炸。

### 工具上千时，定义本身就是检索问题

`tool_search_with_embeddings.ipynb`：>20 把专用工具就开始吃窗口；~100 把以上前置全部定义不现实。做法：先只给 `tool_search` 这把元工具，用本地 embedding（示例 `all-MiniLM-L6-v2`）按自然语言搜，把命中的 schema 当 tool result 返回，模型立刻能调。声明可砍 90%+ 上下文。生产要缓存 embedding、换更大模型提准。`tool_search_alternate_approaches.ipynb` 未进 registry，对照搜索策略时去仓库看。

评测工具本身见 [[10-评测与成本]] 的 `tool_evaluation/`。

对照 recipe：

| 路径 | 钉的是什么 |
|---|---|
| `tool_use/calculator_tool.ipynb` | 最小工具：模型不算，工具算 |
| `tool_use/tool_choice.ipynb` | 强制 / 自动 / 禁用不只是开关 |
| `tool_use/parallel_tools.ipynb` | 一次多工具，延迟和一致性 |
| `tool_use/tool_use_with_pydantic.ipynb` | schema 从类型来，不从散文来 |
| `tool_use/programmatic_tool_calling_ptc.ipynb` | 让模型写代码去调工具，省 round-trip 和上下文 |
| `tool_use/tool_search_with_embeddings.ipynb` | 工具上千时不能全塞进 prompt |
| `tool_use/tool_search_alternate_approaches.ipynb` | 未登记；搜索策略对照 |
| `tool_use/customer_service_agent.ipynb` | 客户端工具的完整环 |
| `tool_use/threat_intel_enrichment_agent.ipynb` | 多源工具 + 结构化报告 |
| `tool_use/vision_with_tools.ipynb` | 看图和动手叠在一起 |

## 关键洞察

工具层有三道闸：**(1) 能不能看见这把工具**（search / 前置列表），**(2) 这一轮许不许用**（`tool_choice` / `allowed_callers`），**(3) 结果进不进模型上下文**（direct vs PTC `excluded`）。只做 (1) 的系统，会在长任务里被自己的 tool result 撑死。

PTC 把「工具」和「上下文」拆开：执行发生在沙箱，模型只吃过滤后的信号。这是第 4 章 compaction 的亲戚——都在问「哪些 token 还值得占注意力」。

## 个人思考

第 1 章用 tool schema 钉输出；本章用同一机制钉行动。区别是副作用。开放 `allowed_callers` 给 code execution，等于把重复执行权交给沙箱——费用查询可以，转账不行。下一章处理工具环必然带来的窗口膨胀。
